## 二、当前数据流和职责

```text
PDF
→ PaperDocument / PaperInput
→ NoveltyPoint[]
→ ResearchTask[]
→ SearchPlan[]
→ CompiledQuery[]
→ SearchHit[]
→ EvidenceCard[]
→ ValidationResult
→ Coverage Assessment
→ 补检或 NoveltyReport
→ Markdown Report
```

| 组件 | 当前职责 | 明确不负责 |
| --- | --- | --- |
| PointExtractor | 从论文提取查新点 | 检索文献 |
| Coordinator | Task 拆分、补检规划、全局汇总 | 数据库查询语法 |
| SearchPlanner | 数据库无关的 Concept 和 Strategy | 执行检索 |
| QueryAdapter | 确定性编译数据库查询 | LLM、网络、补检判断 |
| SearchTool | 执行查询并返回 SearchHit | 证据结论 |
| Researcher | 阅读候选并形成证据卡 | 召回候选、最终新颖性结论 |
| Validator | 质量门控和 Point+Document 去重 | 调用模型修复证据 |
| Workflow | 调度、状态、容错、补检和终止 | 重复实现组件业务逻辑 |
| Renderer | 结构化产物到人类可读报告 | 生成新事实 |

## 三、核心数据契约

### ResearchTask

```python
class ResearchTask:
    task_id: str
    novelty_point_id: str
    task_type: str
    language: str
    description: str
    attempt: int
```

旧 `queries`、`context`、`candidate_document_ids` 已删除。`task_id` 只在 NoveltyPoint 内唯一，所有关联使用 `(novelty_point_id, task_id)`。

### SearchPlan

```text
SearchPlan
├── task_id
├── novelty_point_id
├── SearchConcept[]
│   ├── concept_id = C1/C2/...
│   ├── name
│   └── terms[]
└── SearchStrategy[]
    ├── strategy_id = S1/S2/...
    ├── level = strict/medium/broad
    ├── expression
    └── description
```

SearchPlan 只允许 Concept ID、`AND`、`OR` 和括号，不允许数据库专用字段。

### CompiledQuery

```text
database
task_id
novelty_point_id
strategy_id
level
query
```

## 四、LangGraph 当前拓扑

```text
START
  ↓
extract_points
  ↓
plan
  ↓
plan_search
  ↓
retrieve_candidates
  ↓
parallel_research
  ↓
validate_evidence
  ↓
assess_coverage
  ├── supplement → plan_supplement → plan_search
  └── synthesize → synthesize_report → render_report
                                           ↓
                                          END
```

状态新增：

```text
search_plans
all_search_plans
executed_queries
all_executed_queries
candidates_by_task[(novelty_point_id, task_id)]
```

执行规则：

1. SearchPlanner 按 Task 生成 SearchPlan，单个失败只记录 issue；
2. Adapter 按原顺序生成 strict/medium/broad CompiledQuery；
3. 共享的真实 arXiv SearchTool 顺序执行；
4. 每个 Task 按文献身份去重候选；
5. 候选达到 `candidate_limit_per_task` 后停止放宽；
6. `executed_queries` 只记录真正执行的查询；
7. Researcher 按 Task 分析候选；
8. 证据不足且未达到 `max_rounds` 时，补检任务重新经过完整检索链；
9. SearchTool 不可用时不进入无意义补检。

## 五、Researcher 当前契约

```python
research(
    task: ResearchTask,
    point: NoveltyPoint,
    candidates: Sequence[SearchHit],
    *,
    full_text_tool=None,
    metadata_tool=None,
) -> Sequence[EvidenceCard]
```

Evidence Pack 包含 `document_id`、`title`、`abstract`、`excerpt`、`authors`、`year`、`doi`、`url` 和 `text_source`。

确定性校验：

- Task 与 Point ID 必须一致；
- 空 Candidate 不调用模型；
- DOI → URL → 规范化标题绑定候选；
- 每个非空 quote 必须存在于实际候选文本，且至少有一个有效 quote；
- 错误 task_id/point_id 或候选外文献直接丢弃；
- 同一候选只保留模型返回的第一张卡；
- `cited_by_paper` 统一设为 `None`。

## 六、Adapter 当前实现

`ArxivQueryAdapter` 将 term 编译为 `all:"normalized term"`，同一 Concept 的多个 term 使用 OR，Strategy 的 AND/OR/括号保持不变。

实现使用 tokenizer，不做易出错的 `str.replace()`，并校验非法或重复 Concept ID、未定义 Concept、不支持 token、括号、表达式状态和空 term，同时完成 term 规范化、转义和顺序去重。

## 十二、实验暴露的问题

1. 默认 GLM-4.7 在补检节点返回 403；
2. SearchPlanner 出现 `strategy_strict`、`strategy-1`、`strict` 等非法 ID；
3. 单 arXiv Backend 无法充分覆盖中文查新点；
4. 同步模型调用阻塞异步 Workflow，总耗时接近 18 分钟；
5. V4-Flash reasoning token 偏高，输出达到 92,806 Token；
6. Coordinator 补检和汇总两次调用占全部输入 Token 约 71.7%；
7. 第二轮 Validator 对历史证据重复报告 issue；
8. 需要区分“运行成功”和“证据覆盖完整”；
9. FastAPI TestClient 生命周期测试挂起。

## 十三、下一阶段建议

### P0：可靠性

- 将 Coordinator 默认模型改为可用模型，并增加启动时模型健康检查；
- 稳定或确定性规范化 SearchPlanner 的 Concept/Strategy ID；
- 修复 FastAPI TestClient 生命周期；
- 为模型调用增加统一重试、超时分类和失败 usage 落盘。

### P1：性能与成本

- Agent 使用 `acomplete()` 或在线程池执行同步客户端；
- Coordinator 使用 PaperDigest 和证据摘要，不再传完整 PaperInput；
- 对 SearchPlanner 关闭或降低 reasoning；
- 持久化检索、全文和模型 usage，支持断点恢复；
- 对 Query 和文献全文增加缓存。

### P2：查新覆盖

- 实现 Retrieval Backend Registry；
- 接入 CNKI、万方或其他中文学术数据源；
- 增加跨数据库文献身份归一化；
- 建立 query provenance、rank、score；
- 用论文引用集和人工标注集评估 recall@N、证据准确率与结论一致性。

### P3：生产化

- 用 PostgreSQL/对象存储替换本地 JSON；
- 用 Redis/任务队列替换 InMemoryRunStore；
- 增加 trace、结构化日志、费用预算、取消和限流；
- 明确 `execution_status` 与 `coverage_status`；
- 对报告增加人工复核和版本签名。
