# 第一次原型机实验测试结果

## 1. 实验概况

本次实验是 Novelty Multi-Agent Framework 完成 Workflow 整合后的第一次真实原型机全流程测试。实验使用真实论文、SiliconFlow 模型 API 和 arXiv 数据源，验证如下主链能否完成运行：

```text
PDF
→ PaperInput
→ NoveltyPointExtractor
→ Coordinator
→ SearchPlanner
→ ArxivQueryAdapter
→ ArxivSearchTool
→ Researcher
→ EvidenceValidator
→ Coverage Assessment
→ 补检
→ Coordinator.synthesize
→ Markdown Renderer
```

测试日期：2026-08-09（Asia/Shanghai）。

测试环境：项目专用 `Novelty` Conda 环境。

输入论文：`examples/MF2033k6lC.pdf`。

论文信息：

| 项目 | 值 |
| --- | --- |
| paper_id | `MF2033k6lC` |
| 标题 | 面向大规模动态图的图神经网络优化机制研究 |
| 页数 | 90 |
| PDF 解析方式 | `text_layer` |
| OCR | 未触发 |

## 2. 模型和数据源

本次成功运行使用：

| 职责 | 模型或工具 |
| --- | --- |
| 查新点提取与审查 | `deepseek-ai/DeepSeek-R1-0528-Qwen3-8B` |
| SearchPlanner | `deepseek-ai/DeepSeek-V4-Flash` |
| Researcher | `deepseek-ai/DeepSeek-V4-Flash` |
| Coordinator 补检与汇总 | `deepseek-ai/DeepSeek-V4-Flash` |
| Query Adapter | `ArxivQueryAdapter` |
| 检索数据源 | arXiv API |

原配置中的 Coordinator 模型为 `Pro/zai-org/GLM-4.7`。首次尝试在进入 `plan_supplement` 时收到 SiliconFlow 返回的：

```text
HTTP 403
code: 30003
message: Model disabled.
```

因此，成功实验在运行期将 Coordinator 临时切换到已经配置且可用的 `deepseek-flash`。该覆盖只存在于实验进程内，没有修改仓库配置。

## 3. 最终运行结果

工作流完成了两轮检索与补检，并成功生成结构化报告和 Markdown 报告。

| 指标 | 结果 |
| --- | ---: |
| 工作流轮数 | 2 |
| 查新点 | 3 |
| 累计 ResearchTask | 8 |
| 成功生成的 SearchPlan | 5 |
| 实际执行的 arXiv Query | 15 |
| 原始 EvidenceCard | 11 |
| 接受 EvidenceCard | 6 |
| 拒绝 EvidenceCard | 5 |

最终结论：

| 查新点 | 结论 | 有效证据 | 说明 |
| --- | --- | ---: | --- |
| NP-1 | `partial` | 4 | 现有文献涉及动态图摘要，但尚未发现将图摘要、图自编码器和循环神经网络按论文方案组合的证据 |
| NP-2 | `insufficient` | 0 | 未检索到基于图摘要的分布式 GNN 优化训练的直接证据 |
| NP-3 | `insufficient` | 2 | 证据仅覆盖图摘要相关技术，未充分覆盖论文所述完整组合方法 |

因此，本次实验的准确表述是：

> 主工作流在工程上完整运行并成功输出报告，但文献覆盖并不完整；NP-2 和 NP-3 仍需扩展数据库或改进检索规划。

## 8. 暴露的问题

### 8.1 Coordinator 默认模型已被禁用

`Pro/zai-org/GLM-4.7` 返回 `403 Model disabled`，导致第一次运行在补检节点终止。当前配置需要更换为可用模型，或在启动时增加模型可用性检查。

### 8.2 SearchPlanner 输出 ID 不稳定

模型多次生成不符合 schema 约定的 Strategy ID：

```text
strategy_strict / strategy_medium / strategy_broad
strategy-1 / strategy-2 / strategy-3
strict / medium / broad
```

框架只接受 `S\d+`，因此出现：

- NP-2 / T-2 第一轮规划失败；
- NP-3 / T-2 第一轮规划失败；
- NP-2 / T-R2-2 第二轮规划失败。

现有一次重试仍不能保证恢复。应强化 Prompt 示例，或在不改变策略语义的前提下确定性重编号。

### 8.3 arXiv 对中文和高度限定查询的召回不足

以下任务没有获得 Candidate：

- NP-2 / T-1；
- NP-2 / T-2；
- NP-3 / T-2；
- NP-2 / T-R2-1；
- NP-2 / T-R2-2。

当前仅接入 arXiv，尚无 CNKI、万方等中文数据库，也没有多数据库路由，因此 NP-2 在两轮后仍为零证据。

### 8.4 Researcher 和 Planner 的并发名义上存在，实际模型调用接近串行

Workflow 使用异步节点和 Semaphore，但 Agent 内调用同步 `ModelClient.complete()`。同步 HTTP 请求阻塞事件循环，导致 19 次模型调用大部分串行等待。

### 8.5 Reasoning Token 消耗偏高

V4-Flash 输入只有 141,886 Token，输出却达到 92,806 Token。多个 SearchPlanner 请求的 completion 明显大于 prompt，主要来自模型的 reasoning token。对确定性结构生成任务，应考虑关闭或降低思考强度。

### 8.6 Coordinator 上下文过大

补检规划和最终汇总两次调用共消耗 104,389 输入 Token。应考虑使用 PaperDigest、查新点和证据摘要，避免重复传入整篇论文正文。

### 8.7 第二轮重复报告第一轮 EvidenceValidator issue

第二轮验证累计 raw evidence 时，第一轮的低相关性和重复证据问题再次写入 `issues`。证据结果本身没有重复接受，但审计问题出现重复记录，需要按轮次或稳定 issue key 去重。

### 8.8 报告完成不等于证据充分

工作流已经成功到达 Renderer，但 NP-2 和 NP-3 的最终结论仍为 `insufficient`。系统应在界面和运行状态中区分：

```text
execution_succeeded
```

与：

```text
evidence_coverage_complete
```

## 10. 实验结论

第一次原型机实验验证了新架构已经能够在真实模型和真实 arXiv 数据源上完成两轮闭环：

```text
论文解析
→ 查新点
→ 任务规划
→ 查询编译
→ 真实检索
→ 文献证据分析
→ 证据门控
→ 补检
→ 汇总
→ 报告渲染
```

工程闭环已经成立，但原型仍存在模型可用性、SearchPlan 格式稳定性、中文数据源覆盖、同步调用性能和上下文成本等问题。下一阶段应优先处理：

1. 更换或自动探测 Coordinator 模型；
2. 稳定 SearchPlanner 的 Strategy ID；
3. 将同步模型调用改为真正异步；
4. 压缩 Coordinator 上下文；
5. 增加中文数据库 Backend；
6. 区分“运行成功”和“证据覆盖完整”。
