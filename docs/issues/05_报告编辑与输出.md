## O-02：重渲染不是确定性的（P2，代码确认）

`renderer.py` 第 195 行现场调用 `datetime.now(UTC).astimezone()`。即使输入文件完全相同，重新渲染的时间随当前时刻和本机时区变化；报告未使用冻结生成元数据。现有“确定性 Renderer”只能理解为不调用模型，不满足 T22 的字节/元数据稳定要求。

另一个条件风险：加载器分别读取 paper/points/plans/evidence/report/reference/candidate-audit，未绑定单一运行快照；在同一 paper 工作目录被后续运行覆盖或文件逐项更新时，可混入不同时间的事实。本轮没有制造并发写入实验，故不声称已复现。

## O-03：语义支持矩阵保存在 JSON，却未进入逐点报告（P2，补充）

`report_binding.py` 第 201 行绑定 feature_comparisons；Renderer 第 319–368 行只展示裁定、摘要、相关 Work 和 review_evidence，未消费 feature_comparisons。读者看不到同篇文献对各必要特征的 supported/unknown 对应，也不容易审查为什么不足或为何否定。仅增加可点文献链接不等于表达了技术组合对比。

### O-04：未经语义确认的错误文献贡献仍进入读者报告（P0，新实证）

位置：[renderer.py](../../backend/src/novelty_agent_framework/tools/renderer.py) 第 282–315 行，尤其第 299 行直接输出 card.main_contribution；[integrity_gates.py](../../backend/src/novelty_agent_framework/core/integrity_gates.py) 第 135–203、206–286 行只确认 ID/文件/quote 绑定，不判贡献语义。

真实卡 `card_8ba33651c1b41b8432c27c59` 的标题是 EvoFormer，main_contribution 却为目标查新点的 Sketch-DBH 算法；绑定引文仅说提出 EvoFormer 演化 Transformer。Reviewer 技术失败后该卡仍出现在第六节“主要贡献”，最终整体结论虽明确无法裁定，但卡片断言没有相应未核实标记。Gate A 接受三卡、Gate B 无 issue；这表明语义错误位于现有结构校验范围之外。

原因链：Researcher 生成错误归属 → Evidence/quote 的机械绑定有效 → Reviewer 没有完成语义核验 → Renderer 无条件展示 main_contribution。不能把通过 Gate A 的“有效证据数”解释成文献贡献已获确认，也不能只修最终 verdict 措辞就认为输出可靠。

并发覆盖多个工作文件导致混合快照仍仅为静态风险；本轮未制造该并发条件。
