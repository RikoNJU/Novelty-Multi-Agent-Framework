# 工具失效、not_run 与本地模型：补充因果调查

日期：2026-09-28（原始 JSON 为 UTC）。执行版本 `8fd9c6a`。用户要求补齐模型计划/人工查询以及客户端/网络路径对照，并优先核对两套码的现状。码体系的完整回答见 [错误码与补检/恢复动作状态](code_system_status.md)。

**结论：`not_run` 的直接机制已确认是执行器停止策略；本次 406 不需要小模型参与即可发生。arXiv 拒绝请求的最终根因仍未定位。** 模型检索计划确有质量疑点，但当前所有在线控制都失败，不能估计模型对召回质量的影响，也不能宣称已排除一切模型影响。

本次只新增调查脚本、结果和说明，**没有修改生产代码，没有新增模型调用**。

## 1. 预先固定的条件

- 使用既有真实运行 `run-d55196716d254641a84cf1b0c19f14e9` 的 Qwen 计划与原始响应，不重新生成模型计划。
- 人工控制为 `all:"graph neural network"`，用来观察通路是否能完成一个简单请求，不是与原点语义等价、已确认优于模型的检索方案。
- 线上最多 8 次 GET，仅到 `https://export.arxiv.org/api/query`；无 API key、无自动重试、不跟随重定向。
- 统一 `Accept: application/atom+xml` 和 `User-Agent: NoveltyFramework-Audit/1.0`；start=0、max_results=1；相邻请求开始至少间隔 4 秒。
- max_results 与历史整流程的 8 不同，因此这不是对历史请求的字节级复现；本次组内请求参数保持一致，模型/人工对照只替换查询内容。
- 代码、输入来源及 SHA-256 记录在 [离线结果](offline_results.json) 和 [网络结果](network_results.json)。

## 2. 无模型的执行器因果对照

[offline_probe.py](offline_probe.py) 将 4 个旧 Qwen 计划及每点一个人工计划送入实际 `ArxivQueryAdapter` 和 `StructuredSourceRetrievalTool`，分别注入 HTTP 406、网络超时、HTTP 200 空结果，共 **4 × 2 × 3 = 24 个案例**。计划已显式传入；若执行器调用 planner，脚本直接失败。没有模型和外部请求。

| 注入观察 | 模型计划和人工计划共同结果 |
| --- | --- |
| 首次 HTTP 406 | 只调用一次搜索替身；首条 failed，后续 not_run/provider_failed |
| 首次网络超时 | 同样只调用一次；首条 failed，后续 not_run/provider_failed |
| HTTP 200、零候选 | 执行多条查询，没有 failed/not_run；零结果本身不会触发来源失败停止 |

24 个断言全部通过。现版本编译的 4 个旧计划首查询与原始运行记录逐字匹配。旧基线 `b378e44` 已有 `provider_failed=True` 后跳过后续查询的分支，因此不是本轮新增错误码后才出现的行为。

**确认的因果关系**：在这些案例中，来源调用异常是触发停止的充分条件；模型不参与停止决策。这个实验不证明停止策略合理，更不证明模型计划具有足够检索质量。当前策略把协议错误、瞬时超时等不同错误都在来源调用层停止，是否应区分请求级/来源级故障，是仍需处理的策略问题。

## 3. 真实请求对照

[network_probe.py](network_probe.py) 默认只显示计划，必须显式 `--execute` 才发送请求；已有结果时拒绝覆盖或重复执行。原始响应、状态、时间、选定 headers 和完整 body SHA-256 见 [network_results.json](network_results.json)。8 个响应体均为空，分别保存为 `.body` 文件。

| 客户端 / 路径 | 人工固定查询 | 旧模型 NP-4 查询 |
| --- | --- | --- |
| httpx，环境代理 | 406 | 406 |
| httpx，`trust_env=False` | 406 | 406 |
| curl，环境代理 | 406 | 406 |

另两次：同时间 known-ID `1706.03762` 查询 **406**；最后重复人工查询仍为 **406**。没有成功 Atom 响应。以前 known-ID 200 的历史事实不能用于宣称本次通路健康。

无网络的事后配置检查确认：相同环境中 httpx `trust_env=True` 选择 `HTTPProxy`，false 选择 `ConnectionPool`，见 [实现检查](implementation_audit.json)。这证明客户端显式代理配置不同；**不证明不同公网出口，也不能排除透明代理或共同上游设施**。直接路径与代理路径的响应出现不同边缘节点标识，也不足以确定拒绝发生在哪一层。

这些观察排除了“必须调用 Qwen 或必须使用其复杂查询，才会出现这次 406”的解释；不能排除共同 User-Agent、服务策略、出口/IP 状态、透明网络中间层等因素。所有请求都失败，所以无法比较模型与人工查询的实际召回率或证据价值。本次保持 User-Agent 不变，没有做 UA 因果对照。

## 4. 模型计划确有值得调查的疑点

来源链见 [model_query_lineage.json](model_query_lineage.json)，原始模型响应来自该真实运行的 `llm_calls/0007_local-qwen2.5-7b.json`，不是从最终查询反猜模型输出。

- Qwen 实际给出 `distributed versions of GNN models` 等长术语；它们不只是日志后处理文字。
- arXiv 适配器对超过 3 个词的术语进行逐词 AND 展开，从而生成 `abs:distributed AND abs:versions AND abs:of AND abs:GNN AND abs:models`。**术语来自模型，布尔展开来自程序**，两者不能混为同一个原因。
- 原始模型的 broad 策略选择 4 个概念、strict 选择 3 个概念，并没有自然形成由严到宽的层级。但保存的最终计划已被程序正规化为 strict `C1 AND C2 AND C3`、medium `C1 AND C2`、broad `C1`。不能把原始 broad 的问题直接当成已发往 arXiv 的最终策略。
- 正规化后的 broad 仍只保留目标方法名 `DSGNN framework`。这提示“围绕目标方法专名、缺少可迁移技术机制”的潜在覆盖风险；在没有成功搜索结果和已知相关文献基准前，不能量化损失或将其认定为 406 根因。

离线结果另保留同一计划在旧短语渲染方式下的查询，便于后续独立消融；本次没有切换生产配置，也没有声称改成整句短语就能修好检索。
