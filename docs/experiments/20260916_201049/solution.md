## 3. 原因一：成功检索之后，全文预取占满共享队列

代码路径：

- `tools/database_search/structured_retrieval.py`：数据库调用返回前，直接取
  `enriched_hits[:full_text_limit]`，默认最多 8 篇，等待 `_fetch_full_texts` 全部结束。
- `_fetch_full_texts` 的 semaphore 是每个检索调用内部创建；三个研究任务各自
  并发 4，可能同时向同一 provider 提交约 12 个全文请求。
- `providers/arxiv_web.py` 的 `_get_request` 使用进程级共享 gate，搜索和全文
  一起排队，实际请求至少间隔 8 秒。增加上层并发不能增加此通道吞吐量。

本轮 29 次物理请求首尾发出跨度下界是 `(29-1)×8 = 224 秒`，实际 arXiv
事件窗口 **226.13 秒**，已经非常接近节流下界。实际网络耗时累计只有 **46.20 秒**。
因此不是本轮 arXiv 服务器每次下载都特别慢，而是请求量和共享节流形成等待。

三个首轮 arXiv 数据库调用分别耗时：NP-3 **153.37 秒**、NP-1 **180.79 秒**、
NP-2 **226.06 秒**。最长研究任务 NP-2 总计 391.97 秒，其中该数据库调用占约 58%；
余下还包括模型决策、Reader、其他检索和格式/引文修复。

另有 **2 条 full_text budget_exhausted** 事件，发生在排队而非 HTTP 重试；
实际成功物理请求的最大等待约 **86.82 秒**，逼近 90 秒预算。

注意统计口径：本轮 `queue_wait_ms=1,656,104` 是并行请求各自等待时长的累计，
不能说工作流被队列“额外阻塞了 1656 秒”。B 同样有 1550 秒累计等待，但整体只有1083秒。
`total_arxiv_elapsed_ms` 是事件首尾跨度，B 的 581 秒还包含任务间隙，也不是纯下载时间。

### 预取利用情况

B：22 篇不同论文的全文最终落盘，最终 Card 引用涉及 1 篇全文和 2 篇摘要。
C：23 篇不同论文的全文落盘，最终引用同样仅涉及 **1 篇全文**；此外使用摘要和已有缓存。
这不证明其他全文完全无调查价值，但说明“相关性判断之前固定预取八篇”有明显优化空间。

当前已有摘要元数据缓存、全文完成结果缓存和同任务完整成功检索结果复用；本轮确实
命中了一次检索结果复用。不能把这些已有机制当作尚未实现。缺口在于按需获取、
跨任务正在进行的相同请求合并，以及部分成功调用内部的查询级复用。

## 4. 原因二：慢模型请求是独立且显著的关键路径

| 角色 | A 的请求中位数 | B 的中位数 / 最慢 | C 的中位数 / 最慢 |
| --- | ---: | ---: | ---: |
| Researcher | 2.02 秒 | 2.62 / 152.45 秒 | 4.4 / 59.42 秒 |
| Reviewer | 8.33 秒 | 8.47 / 144.94 秒 | 8.6 / 167.60 秒 |

中位数没有成倍放大，但少数长尾请求会拖住整个阶段的结束。

- C 的查新点提取在任何数据库调用之前就花了 **211.39 秒**；其中一条模型请求
  用了 **181.62 秒**，不能归因于 arXiv 或 Browser。
- B 首轮 Reviewer 最后一次汇总调用耗时 **130.87 秒**；第二轮一个单卡回读后的
  模型调用耗时 **144.94 秒**。并行并没有消除等待最慢卡/汇总的影响。
- C 的 Reviewer 有 **102.69、139.91、151.56、167.60 秒**的请求，输入仅约
  1357–3776 tokens、输出约 731–2760 tokens，不支持简单归因为输入全文过长。
- C 的报告综合只有一次模型调用，但仍用了 **87.27 秒**。
- C 只有94次模型调用，少于A的98次，总时间仍是约3.46倍；不能只优化调用次数。

日志能确定耗时位于模型调用中，但没有首字节时间、连接/读取分段耗时和服务端
排队指标，**不能进一步断言一定是 SiliconFlow 排队、网络还是模型推理变慢**。
Researcher 已关闭 thinking，B 的152秒长请求 reasoning_tokens=0，也说明单纯
关闭 reasoning 不能保证消除长尾。

### 格式修复的额外往返

C 的 Reviewer 有7张卡、7次Reader、3次汇总，但共23次模型调用。按当前成功路径：
每卡至少一次结束调用，加每次Reader后的往返、每点一次汇总，共应17次；额外6次
对应代码中的单次 `repair_json` 路径。这是依据代码和调用数推算，日志未单独打
repair标签，不能给每次修复耗时做无歧义归属。

Researcher 的 NP-2 任务明确记录一次格式修复和一次引文纠正，后者未恢复额外卡。
原始引文不匹配被正确阻止进入最终报告，不能为提速跳过该校验。

### 超时的配套问题

单卡外层 `wait_for` 是240秒，但 `_review_point` 使用的模型HTTP超时可为600秒；
`backend/env/model_client.py` 的异步调用基于 `asyncio.to_thread`。外层取消
不保证线程中的HTTP请求停止。因此后续不能只降低外层超时，必须一起约束实际
传输超时/剩余阶段预算，必要时换为可取消的异步HTTP实现。本轮未发生单卡超时，
此项是确认的实现风险，不是本轮已发生的卡死原因。

## 5. 解决方案与实施优先级

### P0：减少预取请求，保留8秒节流

1. 候选召回数量仍保留8，先保存检索页元数据和摘要；不要在返回候选前默认等待八篇全文。
2. 首批只为相关性最高的2–3篇获取全文；后续 Reader 需要的原文再通过明确的获取步骤补齐，
   持久化 Artifact 后才允许构造 Evidence。不能只调低上限却不给后续取证留入口。
3. 初始三任务若从每个8篇降为3篇，可少安排15个全文请求槽，名义上约120秒的节流容量；
   这是容量估算，不是已实测的端到端节省，后续补取会消耗其中一部分。
4. 为 arXiv 设置统一的待处理队列和公平调度，搜索/摘要优先、全文分批进入；不要让三个
   局部 semaphore 各自灌入四个任务。保留共享 gate，不通过增大并发或缩短间隔破坏限流修复。

### P1：治理模型长尾与结构化输出

1. 为提取、单卡、汇总、格式修复分别设预算；让单次HTTP超时不超过阶段剩余预算。
   可评估60–90秒单次上限、最多一次恢复，但须验证降级比例；不能以超时来伪造已完成审查。
2. 对纯格式修复明确禁用 thinking，使用较小输出预算；主审是否禁用需评估判定质量。
3. 在提示词中提供 reviewed / insufficient_evidence 两个合法JSON示例，明确跨字段约束；
   JSON Schema 本身并不表达全部 Pydantic model_validator 语义。仅做不增加事实的保守规范化，
   不取消原文、身份、引用绑定校验。
4. 在已有模型客户端/原生runtime中增加阶段角色（card/summary/repair）、point/card ID、
   请求开始/首字节/完成时间、超时及finish_reason记录，区分排队等待与输出生成。

### P2：复用已做工作，减少低收益往返

1. 在已有全文完成缓存之外增加进行中请求合并，同一provider/id/version只允许一个获取者，
   其他任务等待同一个结果；临时失败仍可重试，不能永久负缓存。
2. 以规范化query+参数复用成功的子检索，而不是整次bundle只要partial就全部重做。
3. 同一Card/Evidence、point、模型和prompt配置未变时，复用单卡结果；补检后只审新增或变化卡。
   B第二轮没有新增有效卡却重审，存在可消除的重复；C只有一轮，没有这项已发生开销。
4. 将“可比较的局部相关证据”和“完整技术组合已公开”分开，避免为了寻找全特征匹配反复
   阅读后仍零卡。本轮批量Reader27次中24次只有一段，仍可更好地合并已明确需要的读取。
5. 强制Reader期间仅暴露合法下一步工具选择，减少模型先提出被Harness拒绝的搜索调用。

### 验收方式

继续使用现有运行入口；固定PaperInput、点集/缓存和模型配置后分别验证每项改动，
同时检查关键路径、物理请求数、全文最终引用率、有效卡覆盖、引用校验、降级率。
不能只以“更快”判定优化成功，也不能把某次低服务端延迟当成代码优化收益。

## 6. 本轮错误与局限

- 5次Harness前置拒绝：数据库返回候选后模型尝试继续检索，未先Reader；没有发送相应数据库请求。
- 1次未知Artifact ID读取失败；后续继续完成工作流。
- 1条不匹配原文的候选卡被丢弃，格式/引文恢复过程已记录；最终7张卡的完整性门通过。
- 原生Reader/namespace诊断仍将批量结果报告为INCOMPLETE_RECORD等，Reviewer诊断也显示0调用；
  这与工具/LLM事实记录和最终完整性检查不是同一口径。诊断器应兼容read_results和两阶段Reviewer，
  不能据这些汇总字段断言真实读取失败或Reviewer没有执行。
- Browser实际0次调用，未获得抓取成功/失败样本；本轮只能确认其注册和配置，不声称已验证可用性。
