# 论文查新 Multi-Agent 框架演进总结

本文记录框架从确定性 Demo 到第一次真实原型实验的主要架构变化。接口和逐文件细节见《开发进度》。

## 一、初始阶段：总分总 Demo 骨架

最初版本只有：

```text
Coordinator → Research Agent → Evidence Validator → Coordinator.synthesize
```

所有组件都是确定性 Demo。Researcher 同时承担任务理解、检索和证据生成，数据契约中混有 `queries`、`context` 和候选 ID，组件边界不清晰。该阶段证明了 LangGraph 循环结构可行，但不能证明真实查新能力。

## 二、基础能力填充

### 模型与配置

- 建立统一 OpenAI-compatible 模型客户端；
- 增加 `ModelProfile`、`ModelRegistry` 和角色级模型选择；
- 增加版本化 PromptLibrary；
- 支持文本和 OCR 多模态消息；
- 使用 `backend/.env` 或环境变量加载 API Key，密钥不进入 Git。

### PDF 处理

形成：

```text
PDF → 文本层质量判断 → OCR 兜底 → 文本规范化 → 章节切分
    → 标题、摘要、关键词、参考文献 → PaperDocument / PaperInput
```

`MF2033k6lC.pdf` 的 90 页文本层解析、标题和 91 条参考文献提取已经实测。

### 查新点提取

PointExtractor 从论文摘要视图生成 NoveltyPoint，并通过第二次判定式审查去重。中英文 claim 和 technical features 为双语检索提供输入。

## 三、数据契约重构

旧 ResearchTask 中的检索词和候选文献字段被移除，职责收敛为：

```python
ResearchTask(
    task_id,
    novelty_point_id,
    task_type,
    language,
    description,
    attempt,
)
```

新增数据库无关检索结构：

```text
ResearchTask → SearchPlan
               ├── SearchConcept[]
               └── SearchStrategy[]
```

Task ID 只在单个 NoveltyPoint 内唯一，Workflow 和 Validator 全部改用 `(novelty_point_id, task_id)`。

## 四、Agent 职责收敛

### Coordinator

- `plan()`：每个查新点确定性生成中英文 ResearchTask；
- `plan_supplement()`：根据覆盖缺口生成补检任务；
- `synthesize()`：基于全局证据生成 NoveltyReport。

### SearchPlanner

新增 SearchPlanner Agent：

```text
NoveltyPoint + ResearchTask
→ Concept、term、strict/medium/broad 策略
→ 数据库无关 SearchPlan
```

它不能输出 arXiv、CNKI 等数据库字段语法。

### QueryAdapter

新增确定性 Adapter 层：

```text
SearchPlan → ArxivQueryAdapter → all:"..." AND/OR ...
```

Adapter 使用 tokenizer 展开 Concept，避免 `C1`/`C10` 前缀替换问题，并校验未定义 Concept、非法 token、括号和空 term。

### Researcher

Researcher 从“检索 + 阅读 + 比较”收敛为：

```text
ResearchTask + NoveltyPoint + SearchHit[]
→ 全文/摘要证据包
→ 单篇候选独立比较
→ EvidenceCard[]
```

它不再依赖 SearchTool、SearchPlanner、Adapter、PaperInput 或旧 retrieval 路径。证据必须绑定候选 DOI、URL 或标题，quote 必须存在于真正发送给模型的候选文本中，`cited_by_paper` 强制为 `None`。

## 五、Workflow 正式整合

当前 LangGraph：

```text
START
→ extract_points
→ plan
→ plan_search
→ retrieve_candidates
→ parallel_research
→ validate_evidence
→ assess_coverage
  ├─ supplement → plan_supplement → plan_search
  └─ synthesize → synthesize_report → render_report
→ END
```

Workflow 新增：

- `search_plans / all_search_plans`：数据库无关检索计划；
- `executed_queries / all_executed_queries`：真正提交给数据库的查询；
- `candidates_by_task`：按复合 Task key 保存当前轮候选。

检索按 strict → medium → broad 执行；候选达到上限后提前停止。只把实际调用 SearchTool 的 CompiledQuery 记入审计记录。补检不再直接进入 Researcher，而是重新经过 Planner、Adapter 和 SearchTool。

## 六、产物与报告演进

旧的零散 `output/` 文件被替换为按论文隔离的工作目录：

```text
outputs/<paper_id>/
├── paper-input/
├── novelty-points.json
├── retrieval-plans.json
├── evidence-cards.json
├── report.json
└── report/<paper_id>-report.md
```

`retrieval-plans.json` 同时保留 ResearchTask、SearchPlan 和实际执行 Query。Coordinator 的结构化汇总写入 `report.json`，确定性 Renderer 在工作流末尾生成 Markdown。

## 七、Demo 与真实装配

离线默认工作流已经经过完整新链：

```text
DemoCoordinator → DemoSearchPlanner → ArxivQueryAdapter
→ DemoSearchTool → DemoResearchAgent
```

真实组合根装配 PointExtractor、Coordinator、SearchPlanner、ArxivQueryAdapter、arXiv 三工具、Researcher、Validator 和 Renderer。

## 八、第一次真实原型实验

2026-08-09 使用 `examples/MF2033k6lC.pdf` 完成两轮真实流程：

| 指标 | 结果 |
| --- | ---: |
| 总耗时 | 1,076.034 秒 |
| 模型调用 | 19 次 |
| 总 Token | 239,075 |
| 理论费用 | 约 ¥0.33 |
| 实际查询 | 15 条 |
| 原始 / 接受 / 拒绝证据 | 11 / 6 / 5 |

NP-1 得到 `partial` 结论；NP-2、NP-3 为 `insufficient`。这说明工程闭环已经成立，但真实证据覆盖仍受数据源和规划稳定性限制。

详见：[第一次原型机实验测试结果](issues/第一次原型机实验测试结果.md)。

## 九、当前状态判断

> 框架已经从“多个独立模块”演进为“能调用真实模型和真实 arXiv、完成补检并输出报告的第一版原型”，但尚未达到生产级可靠性和科技查新覆盖要求。

下一阶段重点：

1. 替换已被禁用的默认 Coordinator 模型；
2. 稳定 SearchPlanner 的 ID/schema 输出；
3. 将同步模型调用改为真正异步；
4. 压缩 Coordinator 补检和汇总上下文；
5. 增加中文数据库和多 Backend 路由；
6. 修复第二轮 issue 重复累计；
7. 修复 FastAPI TestClient 生命周期挂起；
8. 建立真实论文集的 recall、证据覆盖和结论质量评测。
